gangline

Mushing. The line that joins several harnesses into one team.

Gangline runs Claude Code and Codex as named windows in one tmux session, so they can hand each other work by name and you can watch the whole thing happen.

curl -fsSL https://raw.githubusercontent.com/adambiggs/gangline/main/install.sh | sh

Demo

Every window is a real native harness, not a simulation.

Start

You need macOS or Linux, Bash, tmux 3.2 or later, Python 3, and Claude Code or Codex. Run the harness once first to complete its normal sign-in and repository prompts. Then open a team in the repository where it will work.

cd ~/your/repo
gang up -c claude-code -m sonnet -e high

gang up starts a team and attaches you to its lead window. Detach with Ctrl-b d, then confirm the team is running with gang roster. Add named agents only when the work calls for them.

What it does

  • Delivers work by name

    A message is typed into that agent's own terminal, signed with the sender's name. It reads like anything else you would type there — no side channel, no protocol for anyone to learn.

  • Tells you what actually happened

    A message is reported delivered only once Gangline has seen it land and be submitted, never on the strength of having typed it. Where a harness lets it read the input box, it will not type over a line you half finished. What it reports when a message does not land, and what makes it refuse, is in the reference.

  • Lets you read over their shoulder

    Every agent is a real tmux window. gang attach to watch one work, gang roster to see who is busy and who is waiting.

  • Adds and removes agents mid-run

    Add an agent when a second native session will help, and remove it when its work is finished.

  • Gets a run through the night

    An agent watching its context fill can compact at a checkpoint it chooses and carry on, and one that spends its provider quota can be woken when that quota resets.

What it deliberately isn't: there is no task graph, no supervisor, no daemon, and no database. Gangline connects native agents; it does not manage them. It hands out no work, chases nobody, enforces no deadline, and never answers a permission prompt or loosens a harness's sandbox. Each agent keeps the terminal, tools, permissions, and subscription it already had.

It is also not a replacement for whatever subagents your harness spawns on its own — Gangline operates one level up. A subagent is created and owned by a single harness session, and that ownership is what makes it one. Gangline works between sessions instead: every agent in a team is a separate top-level process running the harness's ordinary CLI in its own tmux window, and one team can put Claude Code and Codex side by side. That is a difference in architecture; what each command does and refuses is in the reference.

Long sessions

Long-running teams eventually meet context and provider limits. Gangline can show context warnings, ask a native harness to compact at a checkpoint, and schedule a one-time continuation after a provider reset. The agent and operator remain in control of each choice.

The operations guide covers configuration and recovery when you need it.
