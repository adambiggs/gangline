gangline

Many CLI agents. One coordinated team.

install· a team of one· how it works· how it compares· commands· extend· the trail· github

gangline is the substrate under a long-running, multi-harness agent team — not the orchestration on top of it. CLI coding agents run as named windows in one tmux session, each used where it is strongest; gang hitches them, proves each attributed message into the target's input box, reads each tug tight or slack, carries them across their own context limits, and drops them when the work is done. One Bash CLI over tmux — no daemon, message bus, database, or harness plugin, and gang exits after every command.

The name is literal. A gangline is the line down the middle of a dog team: every dog is hitched to it by its own tug line, the lead runs out front, and one look down the line tells the musher who is working — a tight tug is pulling, a slack tug is not. That is what the roster below is reporting.

Who does what, and in what order, is your call. It lives in a markdown brief you can replace with a directory of your own; what gangline owns is the layer underneath.

One message to a Claude Code lead: it hitches a Codex worker, waits for the work, then hitches an opencode reviewer to check it. Real harnesses, real subscriptions, unedited except for cuts through the waiting.

Install

$ curl -fsSL https://raw.githubusercontent.com/adambiggs/gangline/main/install.sh | sh

Needs git, tmux ≥ 2.6 and python3. Clones to ~/.local/share/gangline, links gang into ~/.local/bin, re-run to update. Piping a stranger's script into a shell is your call to make — read it first, or clone and symlink bin/gang yourself.

One thing your harness will not tell you. Gangline launches your harness with your own configuration and sets no permission bypass (one small exception for opencode). An unattended agent cannot answer a dialog and Gangline will not answer one for it, so the setting that stops your harness asking belongs in that harness's own config — the README names the one each wants.

Beyond that, the boundary is the machine. Agents on one host already pass text to one another through files, a shared checkout, or each other's panes; Gangline does not create that path, it makes it routine and gives it structure the ad-hoc versions lack — envelopes a body cannot close from the inside, delivery verified in the pane, and a refusal when the input box is not free. Treat every agent's output as untrusted input to the next, and bound the machine if you need a boundary: a container, a VM, a separate account. A separate $HOME is not one.

A team of one

A team can have one dog in it: gang up with nobody else hitched gives you the context loop by itself — measure, warn, act — and needs no permissions decision, because you are attached and watching the pane. 

$ gang up

How it works

Agents are tmux windows.
Hitching is new-window, dropping is kill-window, watching is capture-pane, and the window name is the agent's identity. Attach and you are looking at your team — the pane is the transcript, and you can type into it yourself at any time.
Every message is attributed, and delivery is verified.
A send is wrapped in a [gang:<sender>#<nonce>] envelope whose nonce is minted from a body that already exists, so the body cannot close its own envelope and open another. It is confirmed by capturing the pane, and only then submitted. No sender means no send. Unverified means a loud failure, never a shrug. This is attribution and not authentication — gangline is single-operator software, and anyone who can type into a pane is already trusted.
Agents manage their own context.
A model cannot feel its own token count, so the substrate measures it and warns at configurable bands. The agent compacts itself at the next clean seam, using a detached resume handoff so work continues unattended.
A new harness costs a profile, not a core integration.
The profile owns launch and model syntax, observable busy and occupied states, compaction, mid-turn input, and optional composer and context readers. Profiles observe the stock TUI: a theme or UI extension that repaints it takes a shadow profile of your own (GANG_PROFILES), re-verified against what you actually run.
Batteries included, every one replaceable.
Agents are hitched with a role brief — lead, worker, reviewer. Point GANG_ROLES at a directory of your own and any brief becomes yours.

Where this sits

gangline is a substrate, not an orchestration framework. Who does what, in what order, and what happens when one of them stalls lives in the agent and in a role brief you replace wholesale. gangline owns the layer underneath: how an agent is started, how a message is proven into its input box, what may and may not be claimed about its state, and what becomes of its context over the following six hours. The axis is duration, not breadth — a team that finishes inside one context window needs none of this, and a team still working tomorrow morning needs all of it.

Where gangline is the wrong tool. No worktree isolation, no dashboard, no notifications, no history to browse afterwards, no auto-restart — and it is Bash on tmux, so Windows means WSL. Not on that list: no task list, no dependency graph, no retry policy, no supervisor loop, which are absent on purpose because they are the layer above. Every tool in that table solves a real problem, and for several of them the honest answer is “use that one instead” — or “use that one on top of this”. The README says which, and why, along with the constitution laws that put the boundary there.

Measured, not assumed

Delivery is proven into the box. A send reads the target's input box, pastes, and requires the box to have changed; Enter goes in as its own keystroke, and a later read must differ again. Unreadable and unchanged are separate failures and both are loud — a paste stranded by one is reported as an undelivered paste until the box is empty.

“I cannot tell” is a state, not a default. A predicate that could not reach an answer says so rather than returning the convenient one. gangline can establish that a harness-owned UI has taken an input box; who may free it is a different finding, and it does not pretend to have made it. 

$ gang send reviewer --from lead --stdin <<'MESSAGE'
ship it
MESSAGE
gang: 'reviewer' is occupied (authority unknown) — a UI owns its
input box and gang cannot establish who may clear it; a send would act on that
UI instead of landing (gang attach)

Context is measured, not felt. A model cannot feel its own token count, so the substrate reads it through the harness's own introspection and warns on a ladder keyed to how long a context is rather than how full its window is. Measure, warn, act — the substrate does the first two, and the agent does the third, compacting itself at the next clean seam and handing its own successor the thread. 

[gang:patrol] [context-usage] 187k in context — past the
158000-token band. Start no new work. Close what is open, then compact. Your
recall is already degrading: instructions given once earlier in this
conversation are dropping out, and you cannot tell which ones.
Write the handoff to a file, then run:
gang compact worker --from worker --resume-stdin < resume-file
— this queues behind the turn you are in, and the resume is delivered once
compaction settles.

Every one of those is a mechanism you can read rather than take on trust: the measured composer sequence, the band ladder and its absolute bounds, and the detached waiter that keeps a resume out of the turn being compacted are in the README and in operating a team.

The verbs

commandwhat it does
gang up the whole setup, no arguments: hitches lead in the current repo and puts you in the session
gang hitch <name> -p <profile> -r <role> start an agent — the name becomes its tmux window, its identity, and its handle
gang send <name> --from <you> --stdin attributed, pane-verified message read from stdin; delivered mid-turn where the harness takes input during one
gang roster everyone, with harness, state, and context usage
gang status <name> / context <name> / capture <name> one agent's state, window usage, or screen
gang wait <name> [seconds] block for two consecutive idle readings; parked and expired end it too, so read what it printed
gang compact <name> --from <sender> --resume-stdin submit the harness's own compaction command; a detached waiter attempts the resume and reports delivery failure in status. Native command rejection remains the harness's verdict
gang patrol ambient roster sweep from cron: band warnings in, occupancy and refused inbound out
gang cron [--install] the crontab entry that runs the sweep, derived from this install and the overrides in force; installing replaces a stale one in place
gang vet [--probe [profile]] check installed versions, file schemas, and whether the patrol entry still matches this install; optionally launch a real turn on a private tmux socket and fire declared markers
gang adopt <name> -p <profile> register an existing team window without launching or briefing it
gang attach / drop / down watch the team live; end one named window; end the whole session
gang profiles / roles list available harness and brief names

Extend it

A profile says how to talk to a harness; a role says what an agent is for. Neither is an integration, and both are shadowed rather than patched, so a new harness — or a fix for a TUI that moved under you — costs a file of the same name and never surgery on the installed tree. What a profile declares, and how to point gangline at your own, is in the README.

The trail

Every term names something real, and the musher's field guide maps all of it — roles, states and verbs, never rules. The four worth knowing before you start:

on the trailon the team
tight tug / slack tug busy / idle — a pulling dog keeps its tugline taut
hook set occupied — the snow hook is dug in and the team stands anchored, whether the musher set it or it caught on its own
dropped a released window — deliberate and routine; finishing an arc and being released is health, not failure
dog in the basket a finished agent left running instead of released — the anti-pattern dropped exists to prevent

One bash script. Profiles and roles are files you can replace. tmux is not a hack under it — tmux is the substrate, and when the metaphor stops carrying weight, every command still reads literally without it.
